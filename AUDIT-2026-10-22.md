# ImmoGest workflow audit — 22 October 2026

Scope: source after PR #6; syndic, administrator, resident owner, resident tenant,
and provider accounts. Write simulations use disposable synthetic data. No live
resident record or financial journal was edited.

## Corrected defects

| Finding | Resulting behavior |
| --- | --- |
| Tenant dashboard dereferenced another resident's hidden email. | Resident IDs identify the current resident; redacted fields no longer crash the portal. Missing housing has an explicit recovery message. |
| Interrupted or temporarily failed session checks deleted the login. | Only confirmed authentication rejection clears a session. Temporary failures retain credentials and offer retry. |
| Failed data reads appeared as an account without a cabinet. | Data failures have a retry screen without changing the account's assignment. |
| Delayed reads/mutation responses could refill a different identity's cache or overwrite a newer save. | Identity generations reject old responses; committed revisions protect newer cached data. |
| Maintenance file access compared missing provider identifiers and searched arbitrary notes for URLs. | Access requires a real assigned provider or reporting resident and an actual attachment field. Removing assignment removes file access. |
| Residents could try to publish another resident's private file. | New private attachment references require ownership or an authorized existing attachment. Foreign private references are rejected. |
| Named chat recipients could not download private attachments. | Sender and named recipient can open files; unrelated accounts cannot. |
| Storage/database failures produced the same generic save message. | Clear dependency guidance, safe error codes, and request references identify failures. Drafts remain intact; SDK details stay in server logs. |
| History lists with repeated resident IDs failed serialization after eight entries. | Storage identities preserve repeated entries without changing their business fields. |
| Long string chunks could split an emoji and corrupt text. | Chunk boundaries preserve Unicode surrogate pairs. |
| Bulk replacement staged writes while holding database read locks. | Staging happens outside read locks; a short atomic revision comparison activates a complete generation. Conflicting writers retry against fresh state. |
| Replacement could reset or invalidate the revision counter. | Revisions belong to the repository and advance monotonically. |
| Timestamp-only IDs could collide during rapid record/journal creation. | New records use UUIDs; a same-millisecond journal test verifies unique entries and exact balances. |
| Building confirmation promised permanent deletion while the backend archives. | Confirmation accurately explains archival, preservation and restoration. |

The storage codec reads existing encoded records. It does not delete, merge or
renumber historical business records. Financial inconsistencies require explicit
reconciliation; the audit does not invent payments or silently alter history.

The browser suite contains **26 scenarios**. File mode skips the Storage SDK fault
scenario. Cloud simulation runs all 26 against a local Firestore emulator and the
real Admin Storage SDK connected to a loopback GCS protocol double. It checks data
integrity and simulates permission denial/missing buckets. It does not establish
the permissions or existence of the live Google Cloud bucket.

refuses to run without a local emulator and uses a demo project. Test traffic
cannot contact live payment/mail services.

## Deployed service and remaining acceptance

Read-only checks of `https://immogest-174234637104.europe-west1.run.app` returned
HTTP 200 from `/api/health` and `/api/ready`; readiness reported revision 10. These
responses predate this branch's diagnostics. They prove the service answered and
could read its state at that time. They do not prove an authenticated database
write, a bucket upload, or the cause of the screenshot's payment failure.

After deploying this branch:

1. Confirm the Cloud Run revision and run
   `npm run diagnose -- --url https://YOUR-CLOUD-RUN-URL`.
2. As a manager, inspect `/api/diagnostics` in the authenticated browser. It reports
   database/bucket configuration, stable-secret configuration and mail readiness;
   it exposes no secret. Residents/providers cannot access it.
3. Keep one stable `SYNDIK_SERVER_SECRET` of at least 32 characters across instances
   and revisions. Temporary keys cannot preserve sessions or encrypted retry
   receipts across restarts. This cannot safely be skipped in production.
4. Verify that the runtime identity can read/write the intended named database and
   create/read/overwrite objects in the configured private bucket. Do not bypass
   this with a public bucket or container-local storage.
5. Retry an authorized staging attachment. Find its support reference in Cloud
   Logging with `jsonPayload.requestId="REFERENCE"`. `STORAGE_ACCESS` identifies
   storage authorization failure; `STORAGE_MISSING` identifies a missing resource;
   `DATABASE_*` identifies database dependency failure. Other unexpected failures
   retain a reference and a private server log.
6. Set `PUBLIC_APP_URL` to the actual public HTTPS origin. Verify real email delivery,
   Google login, scheduler execution and a restore drill in staging. The old default
   Firebase Hosting address did not serve the app during this audit. Check the
   Hosting service/region rewrite if Hosting is used.
7. Review actual French/Arabic invoices and receipts with representative staging
   records. CMI remains disabled pending a real merchant-tested integration.

The repository still reads aggregate state and serializes writes with a global
revision. The change avoids read locks during staging and protects correctness;
it does not establish unlimited throughput. Partition tenant data, paginate reads,
and load-test before a large rollout. Passing these scenarios is evidence for the
covered paths, not a guarantee for every live integration or future input.
